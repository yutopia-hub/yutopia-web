# 맞춤 윷판 추천 구현

## 현재 사용자 흐름

왼쪽 패널의 **내 여행 보따리 / 추천 여행지** 선택으로 목록을 전환한다. 추천 여행지를 선택하면 전국 관광정보를 조회해 최대 8개의 카드를 보여준다. 기존 추천 버튼과 미리보기·일괄 적용 다이얼로그는 제거했다.

추천 카드는 보따리와 같은 모양과 배치 방식을 사용한다. 드래그, 더블클릭, 카드 선택 후 빈 칸 클릭/Enter/Space로 한 곳씩 놓는다. 이미 사용한 카드는 두 목록 모두 사용 표시가 되며 중복 배치되지 않는다. 목록 전환이나 추천 완료만으로 윷판을 변경하지 않는다. 추천 여행지를 배치해도 보따리에 자동 추가하지 않는다. 게임 진행 중에도 기존 수동 배치 정책을 따르며, 윷을 던지는 동안에는 배치와 목록 전환을 제한한다.

## 데이터 흐름과 전국 후보 수집

- 보따리: `tourApi.js` → `carrierStore.addToCarrier()` → localStorage의 `travel-notice:carrier`. 분류, 좌표, 지역, 제공된 태그와 실내외 정보도 보존한다.
- 전국 후보: `getTourAreas()`의 `areaCode2` → 각 지역의 `listTourPlaces()`/`areaBasedList2` → 추천 엔진. API 근거는 [공공데이터포털 공식 문서](https://www.data.go.kr/data/15101578/openapi.do)다.
- 후보 조회는 키워드나 보따리 포함 여부로 제한하지 않는다. 실제 브라우저에서는 **모든 지역의 최신 목록을 지역당 최대24개씩 수집**한다. TourAPI 전체 자료를 한 번에 내려받아 전수 탐색하는 방식은 아니다. 이 표본에 보따리·기존 배치 장소를 합쳐 후보로 사용한다.
- 동시 요청4개, 개별 요청15초 제한, 전국 후보10분 캐시를 적용한다. 일부 지역 실패 시 성공한 지역으로 추천하고 안내한다. 전체 실패는 오류와 재시도 버튼으로 표시한다. 실제 API 실패를 예시 관광지로 숨기지 않는다.
- `VITE_USE_MOCK=true` 또는 서비스키가 없으면 기존 TourAPI 예시 전체 목록으로 동작하고 패널에 예시임을 표시한다.

## 상태와 저장

`createBoardState()`의 `places`는 보따리·추천·저장된 여행지를 담는 레지스트리다. `carrierIds`, `recommendationIds`와 `source`로 표시할 목록을 분리한다. `getVisiblePlaces()`가 현재 목록을 반환한다. 카드의 ID로 배치하므로 목록 전환과 비동기 갱신이 배열 인덱스를 바꾸어도 다른 관광지가 놓이지 않는다. 목록이나 카드 데이터가 바뀌면 진행 중인 드래그를 정리한다.

`filled: {슬롯번호: 관광지ID}`는 기존 구조를 유지한다. 일반 슬롯은 **1, 2, 4, 5, 7, 8, 10, 11**, START·열쇠·공항은 **0, 3, 6, 9**다. `put()`이 빈 일반 칸과 중복 여부를 검사하며 배치를 수행한다. 추천 목록 로드는 `filled`를 수정하지 않는다.

보드 저장 형식은 `{boardId, cells:[{index,placeId}], places:[배치된 여행지 정보]}`다. 보따리에 없는 추천 장소도 새로고침 후 복원하도록 실제 배치된 항목의 정보만 함께 저장한다. 저장된 `places`는 `cells`에서 참조된 ID만 읽으며, 보따리 목록에는 합치지 않는다. 기존 `cells`만 있는 저장 형식도 지원한다. 게임의 방문 칸, 마일리지·보상 처리와 저장 키는 유지한다.

## 추천 엔진과 점수

`recommendPlaces({carrier, board, candidates, weatherById, visitedIds, config})`는 DOM·스토어·네트워크에 의존하지 않는 순수 함수다. `candidates`는 전국 추천 후보이고, **취향 프로필은 carrier와 board만 사용**한다. 추천 후보의 빈도를 사용자 취향으로 해석하지 않는다. 보따리와 윷판이 모두 비어 있으면 취향은 50점이다. `candidates` 생략 시 기존 보따리·보드 기반 호출도 지원한다.

| 요소          | 가중치 | 계산                                                                                                                                                                                             |
| ------------- | -----: | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 거리          |    30% | Haversine 직선거리 행렬. `100/(1+d/40km)`의 평균75%와 가장 먼 상대 점수25%. 좌표가 없는 쌍은50점                                                                                                 |
| 취향          |    35% | 보따리·기존 윷판의 유형/지역/태그 빈도. 기존 배치는 총1.5배 신호. 후보가 프로필에 있으면 자신의 신호를 제외하고 `50+50*지지빈도/(최대빈도+4)`로 평활화. 사용 가능한 특징에70/20/10 비중을 재분배 |
| 날씨          |    20% | 확인된 실내·야외와 실제 위치의 현재 날씨. 비: 실내95/야외20, 눈:90/30, 맑음:70/95, 강풍36km/h 이상:90/15. 폭염33℃ 이상: 냉방 확인 실내95/그 외 실내50/야외15                                     |
| 다양성·새로움 |    15% | 유형 일치0.7, 세부유형 일치1, 태그 Jaccard 중 최대가 두 장소의 유사도. `100*(1-0.7*최대유사도-0.3*평균유사도)`. 실제 방문 ID가 제공되면15점 감점                                                 |

기본 가중 합에 기존 장소 유지 보너스 최대10점을 더하고0~100으로 제한한다. `baseScore`, `retentionBonus`, `score`, `scores`, `reasons`를 별도로 반환한다. 카드의 툴팁과 접근성 설명에도 추천 점수·이유를 제공한다. 가중치와 기준값은 `recommendationConfig.js`에서 조정한다.

유형은 cat2→cat1→category/c→contentTypeId/typeName 순으로 사용하며 cat3는 세부유형이다. 없는 유형·태그·실내외 여부를 제목으로 추측하지 않는다. 명시적인 `setting: 'indoor' | 'outdoor'`만 날씨 판단 근거로 사용한다. 냉방도 명시적인 `airConditioned: true`만 인정한다.

## 왜 이 8곳인가?

1. 전국 후보와 사용자가 선택한 장소를 ID로 중복 제거하고, 사용자 선택만으로 취향 프로필을 만든다.
2. 우수한 단일 후보와 지리적으로 분산된 후보에서 기본10개의 시작점을 잡는다.
3. 각 시작점에서 한 곳씩 추가하면서 **조합 전체의 거리·다양성 점수**를 다시 계산해8곳을 구성한다.
4. 여러 결과와 현재 윷판이 완성된 경우의 조합을 비교하고, 한 장소를 다른 후보로 교체하는 탐색을 최대2회 수행한다.
5. 선택된8곳 안에서 점수와 실제 계산에 근거한 추천 이유를 다시 산출한다.

따라서 점수는 고정된 개별 순위가 아니라 함께 선택된 조합에 따라 달라진다. 먼 장소는 자신과 다른 장소의 거리 점수를 낮추고, 유사한 장소가 많으면 다양성 점수가 낮아진다. 기존 장소에는 유지 보너스를 주며, 평균 점수 차이가 `5/조합 크기` 이내이면 기존 장소를 더 많이 유지하는 조합을 우선한다. 이후 점수, 기존 배치 여부, 슬롯 순서, ID로 결정적으로 비교한다. 이 정책은 추천 후보 선정에만 영향을 주며 기존 윷판의 장소를 자동 교체하지 않는다.

## 비용과 날씨 정책

후보 수 n, 추천 개수 k≤8, 시작점 수 S≤12(기본10), 교체 횟수 P≤3(기본2)에서 주요 비용은 `O(n²+S²·n+(S+P)·n·k³)`, 거리 행렬 공간은 `O(n²)`다. k/S/P를 상수로 보면 O(n²)다. 전역 최적해를 보장하지 않는 근사 탐색이며 이동 경로 순서도 최적화하지 않는다.

날씨는 기존 Open-Meteo `getCurrentWeather()`를 재사용한다. 여행 날짜 입력이 없으므로 현재 날씨만 사용한다. 실내외 근거와 좌표가 있는 장소만 조회하고 동일 좌표 병합,10분 캐시(최대256개), 동시4개·신규 위치 최대24개 제한을 적용한다. 누락·실패·초과·예시 날씨는50점이다. API 풍속 단위는 km/h로 고정한다. 근거는 [Open-Meteo 공식 문서](https://open-meteo.com/en/docs)다. 게임 내 이동을 실제 방문으로 간주하지 않으며 현재 UI에는 실제 방문 기록을 연결하지 않았다.

## 갱신과 오류

추천 목록은 전환 시 자동 로드한다. 장소를 한 곳 놓을 때마다 목록이 바뀌지 않도록 현재 카드를 유지하며, 다음 추천 목록 진입 시 변경된 윷판을 반영한다. 계산 중 보따리·윷판이 바뀌면 요청을 취소하고 최신 상태로 다시 계산한다. 보따리로 전환하거나 페이지를 떠나면 진행 중인 요청을 취소한다. 오래된 응답은 세대 번호로 배제하고 해제 시 구독도 제거한다. 추천이8곳 미만이면 있는 카드만 표시하며 개별 배치는 가능하다.

## 구현 파일과 검증

- 전국 후보: `src/api/tourApi.js`, `http.js`, `recommendationApi.js`, `recommendationCatalogApi.js`.
- 엔진: `src/recommendation/`의 설정·정규화·취향·거리·날씨·다양성·조합 탐색 모듈.
- 화면·상태: `src/pages/board/recommendation.js`, `placeList.js`, `ui.js`, `drag.js`, `state.js`, `main.js`, `markup.html`, `src/styles/board-recommendation.css`.
- 저장 시 여행지 스냅샷은 기존 `boardApi.js`를 통해 저장한다.
- 검증: `tests/recommendation*.test.js`, `tests/boardPlaceSources.test.js`, `scripts/check-recommendation.js`, `scripts/benchmark-recommendation.js`.

`node --test tests/*.test.js`, `npm run format`, `npm run lint`, `npm run build`를 실행한다. PowerShell에서 npm.ps1이 제한되면 `npm.cmd`를 사용한다. 브라우저 검증은 `VITE_USE_MOCK=true`로 Vite5173을 실행하고 별도 테스트 프로필의 headless Chrome 디버깅 포트9223을 준비한 뒤 `node scripts/check-recommendation.js`로 실행한다. 테스트는 전국 추천·빈 보따리, 목록 전환, 실제 드래그·더블클릭·키보드 배치, 보따리 미변경, 저장·복원, 특수칸·보상 유지, XSS, 모바일, 취소·재시도와 화면 해제를 확인한다.

향후 서버에 전국 관광정보 인덱스를 구축하면 현재의 지역별 표본 대신 전체 자료에 대한 후보 검색을 수행할 수 있다. 상세 실내외 근거, 여행 날짜 예보, 실제 방문 기록, Web Worker와 이동 경로 최적화도 확장 대상이다.
